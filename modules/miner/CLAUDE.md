# Miner Module

Specialized mining behaviors built on the bot module's behavior layer. Two of them: a diamond strip miner that digs a staircase down to the layer 3 blocks above bedrock and tunnels forward chasing ore, and a chunk miner that empties a whole chunk layer pair by layer pair.

## Architecture

```
net.stracciatella.miner
├── MinerModule.java            # Entry point (trivial — see MinerSetup)
├── MinerSetup.java             # Wiring: config, behaviors, commands, GUI pages, tests
├── MinerConfig.java            # GSON-persisted config (miner.json)
├── MinerCommands.java          # /miner subcommands
├── DiamondMinerBehavior.java   # BotBehavior: LOCATE → DESCEND → TUNNEL strategy
├── ChunkMinerBehavior.java     # BotBehavior: SELECT_SLAB → (EXIT) → DESCEND → CLEAR strategy
├── SerpentinePlan.java         # Pure column ordering, unit-testable without a game
├── SpiralStairs.java           # Pure geometry of the ramp left standing, likewise
├── gui/
│   ├── BlacklistPage.java      # GuiPage contributed to the gui module, on its IdListScreen
│   └── MinerSettingsPage.java  # The chunk miner's own two knobs, on its SettingsScreen
└── test/
    ├── MinerTests.java         # In-game tests for the diamond miner (suite not registered for now, see MinerSetup)
    └── ChunkMinerTests.java    # In-game tests for the chunk miner
```

The module never touches input or the camera. `DiamondMinerBehavior` plans steps as batches of `MineBlockTask`s on the bot module's `BotController`, waits until the controller is idle (task executed, drops collected), verifies the result, and plans the next step. All human-like mechanics (camera, timing, tool selection, collection) come from the task layer for free.

`ChunkMinerBehavior` waits for idle too, with one exception: the corridor sweep also plans while the controller is **COLLECTING**, and — since the pace work — while it is still **INTERACTING**. Waiting for idle means the controller sees an empty queue at the end of every column, reads that as "nothing left to do" and collects to completion before anyone can hand it the next block — the loop the user sees as *mine, stand, walk, mine*. Planning early puts a block in the queue, so the moment the drops are in the controller starts the next break instead of standing idle waiting to be handed one; planning during the break puts one there before the collect round is ever entered, which is what `continueSeam` needs to skip it (see *Why the collect round is hard to remove*). Only `CLEAR` runs early: `SELECT_SLAB` is where a run ends, and finishing there would stop the controller mid-collect and leave the last column's drops on the ground; `DESCEND` wants the bot's final position.

The per-column breather draws from `HumanBehavior.randomBreatherTicks`, not `randomTaskSwitchDelayTicks`: the occasional long pause only, nothing the rest of the time. Pausing on *every* column is itself the machine-constant cadence a breather exists to break — and because planning is what releases COLLECTING, it sat in the critical path of every column, measured at 3–6 ticks on top of the collect.

`policy()` returns `BotPolicy.none()`: the strip miner's timing and collection were tuned without any of the bot module's policy opt-ins, and its own fail-fast hazard checks already abort before most of what those guards would catch. Mob *defence* — fighting back rather than stopping — is the right answer for this behavior and is not implemented yet.

## DiamondMinerBehavior

State machine, advanced once per planned-and-verified step:

| Phase | Behavior |
|-------|----------|
| **LOCATE** | Find the highest bedrock in the start column → `tunnelFeetY = bedrockTop + floorOffsetAboveBedrock` (default 3). Tunnel direction = player's horizontal facing at start. Fails if no bedrock below or the player stands below the target level. |
| **DESCEND** | Dig a 1-wide staircase toward the tunnel direction: 3 blocks per step (foot, head, ceiling clearance), one step down per batch, until the cursor reaches `tunnelFeetY`. The player follows the dig front through the controller's own collect-walk and positioning. |
| **TUNNEL** | Before each slice — and only while the player stands at tunnel level (from above, e.g. still on the staircase, the gallery ceiling hides every face from the eye; digging the next slice first pulls him down via the collect-walk) — scan `oreScanRadius` (default 4 = mining reach) around the player for diamond ore. Found ore is mined first via a walkable 1×2 **side gallery** (4-connected columns at tunnel height from the player's column to the ore's column, then the ore — reachable from one below the gallery floor to one above its ceiling; the collect-walk pulls the player in so each next block is frontally visible). Ore veins resolve naturally through the repeated scan. Then dig the next 1×2 slice and advance, until `tunnelLength` slices are done → SUCCEEDED. Air that the run excavated itself (galleries crossing future slices) is tracked in an `excavated` set and never mistaken for a cave. |

### Batch sequencing and verification

A step can consist of several **sequential batches** (`batchQueue`): a staircase step digs ceiling+head first and the foot as a follow-up batch (until the head is gone, every face of the foot is covered and targeting it burns a look timeout or a server-rejected break); an ore gallery digs one column per batch with the ore as the final batch (the collect-walk between batches pulls the player down the gallery so each next column is visible from up close). A single big batch does NOT work: the controller's nearest-task selection reorders it and targets blocks that are still hidden.

After every batch the behavior re-checks all planned blocks. Survivors are re-enqueued up to `maxStepRetries` times (covers task failures; gravel that drops into a cell is the mine task's own next sub-target now — see the bot module's *Falling blocks*). A persistently unbreakable tunnel/staircase block fails the run; a persistently unreachable **ore** (its own task or any gallery batch failing) is skipped, logged, and remembered in a skip-set — one bad ore must not kill the session.

### Fail-fast safety (documented limitations)

Hazards abort the run with a reason instead of being handled:

- **Liquids** ahead of the dig front, behind the next slice, or above the head block (breaking it would pour lava into the tunnel) → FAILED; likewise if a verified block turns out flooded.
- **Bedrock** in the staircase or tunnel slice → FAILED (possible in the jagged bedrock zone; ores behind bedrock are skipped instead).
- **Open cave** ahead (whole slice + the slice behind it air, or an all-air staircase step — own excavation excluded via the `excavated` set) → FAILED — the bot does not walk blind into unlit caves. A single 1-slice air pocket is tunneled through.
- **Out-of-layer or blocked ore** (outside `[tunnelFeetY−1, tunnelFeetY+2]`, gallery crossing bedrock/liquid, or repeatedly failing its tasks) → skipped and remembered, never a run failure.
- **Missing floor** below the next staircase step or tunnel slice → FAILED (no falling into holes).
- No torch placement, no inventory-full handling, no tool-durability handling yet.

## ChunkMinerBehavior

Empties one chunk between two layers, the way a person would: walk a 1-wide, 2-high corridor to the far side, step over one, walk back, and when the level is bare dig straight down through your own feet into the next one.

| Phase | Behavior |
|-------|----------|
| **SELECT_SLAB** | Pick the topmost layer pair inside the range that still holds a diggable block. No progress is stored anywhere — see below. |
| **EXIT** | Once a run, when its top slab is done: carry the staircase on up until it meets the ground outside the chunk, and mend it on the way — see *The way out reaches the ground*. |
| **DESCEND** | Get the feet down to that slab by digging through the bot's own column, one block per batch, so it drops a single level at a time. "Its own column" is the one holding the bot up, not the one its centre is over: `blockPosition()` rounds the centre while the hitbox is 0.6 wide, so with the cell below already open the box can still rest on a neighbour. Waiting for a drop that then never comes froze the run silently — no task queued, so the whole game logged nothing. The wait is bounded and fails loudly. |
| **CLEAR** | Walk the slab's 256 columns in serpentine order, one column per batch (head block before foot block). |

**Resume is the absence of state.** The current slab is derived from the world every time one is needed, so stopping a run — deliberately, by a policy guard, or by losing the client — resumes exactly where it left off, and no saved cursor can ever disagree with what is actually still standing.

Which only works because the range top is the bot's **head** layer. `fromY` is the head layer of the topmost slab — `isMinable` caps there and the slab grid starts at `fromY - 1` — so an argument-less start takes `feetY + 1`. Taking the feet layer anchored the grid one level too low: the layer pair the bot occupies could never be selected, so a run restarted inside a half-cleared slab descended out of it and left the rest of that slab's head layer above the range for good.

`SerpentinePlan` orders the columns: along a row, step over, back along the next, with the first row alternating per slab so a finished slab hands the next one a start next to where it stopped. It is deliberately free of Minecraft types so its two load-bearing properties (every column visited once; consecutive columns adjacent) are unit-testable.

Columns are batched only as far as the pickup box reaches (`CHAIN_DISTANCE`), and the batch is executed **in the order it was planned** — `policy()` opts into `withOrderedTasks()`. The controller's default is to run the task nearest the player, which in a straight corridor targets a block two columns ahead that the near column still hides — the same lesson the diamond miner's batch sequencing encodes, and the reason batching used to be forbidden here outright. The serpentine already *is* a safe order, so insertion order is both the faster and the correct one.

`nextColumn` guards the same hazard for the sweep itself: it resumes at the column **the sweep took last** (`sweepColumn`), runs the snake's direction *to the end*, and only then walks back over what was left behind, nearest first. It never wraps. A forward-only scan with wraparound looks like it keeps the sweep adjacent, but once the work ahead is done the modulo throws the bot to the far corner and it walks back — reaching a column three over while the one right behind it still blocks the line of sight, and the run dies on a look timeout.

**The anchor is the sweep's place, not the bot's feet.** They agree while the bot mines and part company while it collects: it walks after cobble, vanilla scatters a drop up to half a block off the column it fell from, and the breather between columns is random, so now and then the scan runs while the feet are in the row next door. Anchored there, it finishes that row and enters the row it was actually clearing *from the far end* - neighbouring rows are entered from opposite sides, that being what a serpentine is. The corridor test failed about one run in ten with `cannot break 3019, 41, 3015 (blocks mined: 2)`: 3016 cleared, 3019 handed over, 3017 and 3018 still standing in the line, and nothing able to walk the bot to it. Anchoring on `sweepColumn` costs one field and cannot drift; the bot's cell stays the fallback for a slab's first column, where the sweep has no place yet and the bot has just descended into one. `keeps its place when the bot steps out of the row` pins this: it moves the bot a row north the moment the first column falls, client-side because no command round-trip beats the scan, and asserts the order the corridor comes down in. Reverted to the old anchor it reproduces the original abort verbatim.

**Occlusion was tried here first and reverted.** Substituting the column standing on the line to the target - dig your way through, since it is work either way - fixes the corridor case too, but it fires on a corner clip as readily as on a wall: the collect-across-a-pit test reordered from `3014,3015,3016,3017,3018` to `3015,3016,3014,3017,3018` and stranded three drops. Line of sight from the feet is not the controller's question - it aims at a face and may walk - so the miner second-guessing it costs order for nothing. What survives is `columnInTheWay`, now the controller`s own clip and used only to name the obstacle in the retry line: `still standing in the way: 3018, 40, 3015` where it used to say `nothing to mend on the way there`, true and useless.

### The two ways the sweep departs from a clean serpentine

Both were logged (`SWEEPORDER`: bot column, its snake index, the column handed over, its index) on the aim test's 7×3 patch, entering at index 120:

```
[121][122][123] → [133][134] → [132] → [135][136][137][138] → [119][118][117] → [106]…[100]
```

**The entry-row stub.** The bot enters a slab wherever it descended, so its own row is the one row the snake cannot hand it whole: `119,118,117` — the half of the entry row behind the bot — is mined a whole row late. In a full chunk that stub is up to half a row. Sweeping the row's own leftovers first fixes it and was tried: it turns the entry row into one there-and-back, out to that end, turn, all the way to the other, after which every row runs end to end. It was **reverted** — the walk back over the stub cost 0.7–3.4 ticks per block and ~500° of yaw across three runs of the aim test. It is a fixed cost per slab (under 1% of a 256-column slab, a fifth of a 20-column fixture), so the pace tests systematically overstate it and cannot settle the question.

**The deferred turn — fixed.** `132` is the column where the row turns, and it used to be mined after `133`/`134`. The bot mines from a standstill out to reach, so at a turn it stands two columns short of the row's end and its line to the diagonal corner runs through the column beside it; `nextColumn` skipped it and the sweep turned back for it, one extra turn per row.

Mining ahead and turning late are the same mechanism — the bot is fast precisely because it clears everything within reach without stepping, and that is why it is never at the row's end when the row turns. So the fix is not in the sweep but in the controller: `BotPolicy.withApproachOccluded` makes it walk until the sight line is clear, and the sweep hands hidden columns over in their place instead of skipping them (`isAimable` and the deferral are gone).

Waiting for the collect walk to carry the bot there was tried first and reverted — **the pace work had removed the walk it waited for.** COLLECTING is down to 5 ticks in a whole 20-column run, so at a turn there is no walk left to finish; the order went from `133,134,132` to `134,135,132+133`, no cost and no benefit.

With the approach the turn reads `…123 → 132,133,134 → 135,136,137,138`: the corner first, and close enough to chain its neighbours into the same batch. Measured over two runs — **20/20 at 13.8 and 19/20 at 14.5, yaw 884 and 865 against 1067–1107 before**. It buys the order for nothing and takes about 18% off the head-turning, because a turn-back is more yaw than a short walk.

Running forward *to the end* is the part that matters, and it replaced trying the snake's direction first **at each distance** (`start+i` then `start-i`). Alternating like that is invisible while the bot walks, but a whole group of columns inside `reachDistance` (~4.5 blocks — a 2-high corridor is dug several columns deep without a step) is mined from a standstill: `start` never moves, so every column dug hands the next turn to the other side and the bot ping-pongs across itself. Measured with the bot at x=3015, it dug 3016, then 3014, then 3017 — three ~150° head turns in a row. LOOKING is the phase where the pickaxe is idle, so that is also three gaps in the mining; both symptoms were reported as one. Any ordering heuristic derived from the bot's position has to ask whether the bot actually moves.

It also defers a column that is **in reach and occluded**. Skipping an empty column leaves the bot standing diagonally to the next one with the orthogonal neighbour still up, and nothing walks it clear: the controller only navigates to targets out of reach, and the post-timeout re-approach closes to two blocks, which the bot already beats. The occluder is itself a column of this sweep, so digging it first opens the sight line, and since the miner keeps no cursor the deferred column simply comes back. Out of reach counts as visible — the controller walks to those, and where it ends up is not knowable at planning time. If only the occluded column is left it is returned anyway, so a genuinely unbreakable block still fails the run.

### The staircase out (`SpiralStairs`)

A bot that has cleared twenty slabs is forty blocks down a sheer 16×16 shaft, and no amount of pathfinding gets it out: a mesh edge climbs at most **one** block (`ChunkMeshBuilder.isBlockReachable` refuses `dy < -1`) and drops at most three. So one cell in every layer is never mined, and those cells form a ramp.

`SpiralStairs` is a **pure function, not a plan**. Nothing is stored, nothing is built up front, and no cursor records how far the ramp has got: given a position, `isStairCell` answers whether that position is a step. That is the same principle the rest of the chunk miner runs on — progress is read back out of the world rather than remembered — and it is what makes the answer identical for the three callers that have to agree: the sweep deciding what to skip, the finish condition deciding whether a slab is done, and the repair deciding what to put back. Three callers agreeing because there is only one answer to agree with.

**The layer alone decides which column, and it used not to.** The ring position is `-y mod 60`, pinned to the world's own height grid. It was once counted down from a `topY` that `start()` took from wherever the bot happened to be standing, which made the ramp a property of the *run* rather than of the chunk — and any second start moved it. Reported as a staircase mined away at every layer, and the log said it outright: `staircase from y=103` on one run and `staircase from y=101` on the next, in the same shaft, because the bot had descended two blocks before the run was started again. Every step in the shaft rotated by two, so the sweep mined the ramp it had left on the way down and spared the neighbouring cells instead. It is not only a person restarting a stopped run: **resume is `start()`**, so a restock trip did it too, unprompted, in the middle of a run. A chunk miner that finds its place again by reading the world cannot have geometry that depends on when it started reading.

It is **pure in its arguments too**: the geometry is chunk-local integers with thin `BlockPos` overloads on top. Not a style preference — constructing a `ChunkPos` outside a running game throws from its static initialiser, so a signature taking Minecraft types cannot be unit tested at all, and geometry this load-bearing is exactly what wants testing without a game. Same reason `BotAlarm.isAttackerInRange` takes bare doubles.

**The geometry**: one step per layer, walking the chunk's *outer* ring — 16 along the north edge, down the east, back along the south, up the west, `RING_LENGTH` = 60 cells, each horizontally adjacent to the next and the last adjacent to the first. The step one layer down sits one ring position further along, so the ramp falls at exactly the 1:1 slope the mesh can climb, and a full circuit ends 60 blocks deeper directly under where it started. The outer ring rather than a tighter spiral because its outward side is the chunk wall, which is never mined: every step has rock on one side and the shaft on the other, the way a quarry staircase does. A ring further in would be a free-standing ledge with a drop on both sides.

**Where the ramp stops is a second question, and it is `isStep`'s** — the geometry answers only which column. The top two layers of a range carry no step: they are the pocket the bot is standing in, air both of them on every argument-less start (`fromY` comes from the bot's head), so a ramp reaching into them would have `repairStairs` building a step in mid-air on the first tick of every run. The ramp starts at the floor, which is also the level the bot walks off it onto.

**Unless a step is already standing there**, and that clause is what keeps a resumed run honest. Its own pocket is two layers deep in ground the previous run already cleared, and the only thing left standing in those two layers *is* that run's staircase — so "already solid" is how this run recognises a step it did not place. Without it the ramp keeps a two-layer hole at every point a run was restarted, which is the same bug as the rotating phase above, smaller. Reading the world is how the miner finds its place again everywhere else; the ramp is no exception. Falsified by dropping the clause: `keeps the staircase when a run starts again lower` fails on both steps.

**One seam.** `isMinable` is the single place the exclusion lives, so nothing else in the miner has to remember the ramp exists — the sweep skips those columns, and a slab whose only remaining blocks are steps counts as done. `repairStairs` asks `isStep` too rather than re-deriving the cap, for the reason the whole class exists: two spellings of one rule disagree eventually, and here that means one half building what the other mines.

**The cell under a step is the ramp's first cost, and it is paid by `hasOpenFace`.** A step is never mined, so the cell beneath it has a lid no batch will ever lift — and the next step down stands on the *next* ring cell along, which covers a second face. In a slab that is still solid the other two are rock, so at the moment the sweep arrives there is no face to aim at at all. `faceTowardPlayer` then does what its own javadoc says it does when every candidate is covered: it hands back the dominant face anyway, "callers clear the blockers first" — and this caller cannot, because the blocker is the staircase. The bot climbed onto the step, aimed at the lid under its own feet, and the run died on `cannot break -30, 84, -64 (blocks mined: 1334)` with the hit result naming the step in all three attempts. So a cell is only planned once one of its top or four side faces is open, or is about to be because the same batch takes that neighbour out first — which is the head-before-feet order generalised, since that order exists for exactly this reason one layer up. Asked in all **three** places `isMinable` is asked (`addColumn`, `hasWork`, `slabHasWork`), and that is not optional: a slab that reports work no column will accept loops SELECT_SLAB → CLEAR → SELECT_SLAB forever, which is a hang where the old behaviour was at least a clean failure. Deferring is not the skip-after-failure that STR-063 rejected: nothing is given up on, the cell stays work, and the column that opens it takes it along (see *A waiting cell goes with the column that opens it* below). Only a cell still sealed when the rest of the slab is mined — wedged between the ramp and bedrock or a blacklisted seam — is left standing, and then it really is unreachable.

**An opening no body fits through is not a face**, and the same cell reported it a second time: `cannot break -16, 106, -64 (blocks mined: 138)`, at the chunk's own corner. Overhead the first step, east of it the second, south of it unmined rock — and west and north the cell opened straight out of the chunk, where the quarry's rim leaves air at the slab's level with standing ground over it. A ray goes through that; a body cannot, and the bot has no business out there in any case — nothing outside the chunk is ever mined, and the floor the sweep works from stops at the border. Both counted as faces, so the cell was planned, and the nearest the bot could get to it was up the staircase and onto the lid: `face=west … hitResult=-17, 107, -64 (up)`, then twice more with the hit result naming the step under its own feet. So a **side** neighbour now also has to lie inside the chunk; the top face needs no such test, being this column's own cell. Deferred, the cell is mined from the south a few columns later, from inside the slab and at eye level, which is the same back pass the rule above relies on. Requiring the cell *above* an open neighbour to be open too — a body is two cells tall, so a gap under rock has nowhere to put an eye — was written first and reverted, because it is only true out at a rim: above the head layer of the **topmost** slab stands rock the range does not cover, so a run started under a low ceiling would have deferred every head-layer cell for good and `slabHasWork` would have called that layer finished. In-chunk neighbours need nothing asked of them anyway — the sweep takes whole columns, and a bot standing in the slab carries its eye in the head layer, level with the face.

**A top face is a face only to an eye above it**, and the rule got a third cell wrong through that: `cannot break -1, 103, -61 (blocks mined: 25)`, `face=up`, three look timeouts from one spot with the hit result on the step. The cell sits **over** the lower step, with the upper step beside it, and the sweep turned into its row right there while the rest of that row and the next still stood — its top was the only thing open. On the slab's floor the eye is 1.62 up, inside the head layer: over a foot cell's top and under a head cell's. A head cell's top is the floor of the slab above, air on every slab but the first, so counting it had made the rule say yes to the whole head layer. `hasOpenFace` now takes the layer the aiming bot stands in and counts the top face only for a cell at or below it. The sweep (`addColumn`, `hasWork`) asks from the slab's floor; `slabHasWork` asks from the bot's actual feet, and has to: from the slab above, a head cell's top is what the bot looks down on and the only way into a slab nobody has opened, so asked from each slab's own floor every untouched slab under the bot would read as finished and the run would end after one. For the slab the bot stands in the two questions are the same one, which keeps a cell only its top opens out of the SELECT_SLAB → CLEAR loop.

**A waiting cell goes with the column that opens it**, and that same cell is what showed it: `-1, 103, -61` left standing beside the ramp, no abort, while the sweep worked west along the row it starts. Deferring it was right; the trouble was what came after. On a forward pass that cell is the first column of its row, and the column that opens it is the very next one in the snake — but `nextColumn` never looks behind the sweep until the back pass at the end of the slab, so the cell waited a slab's worth of work. Now every column that is planned, and every one the chain adds, offers the column before it once more (`addColumnBefore`), and a cell it opens falls straight after it, from the same spot. Three conditions keep that offer to the waiting cell:

- **The sweep went past it.** The chain always has. The planned column has only when `nextColumn` found it scanning forward from the sweep's place (`scanStart`). On a back pass the column before is the next one the pass has to take, and offering it batches that column past `CHAIN_DISTANCE`, which is the batching that bound exists to prevent. Two weaker forms were tried first:
  - *Offered unconditionally.* The corridor test clears its corridor on a back pass, because the corridor lies behind the bot in snake order, and it took its next column in from two blocks out.
  - *Offered only when that column had nothing to take on its own.* The staircase fixtures, whose bot enters at the snake's end, took whole columns of sealed rock along their back pass. Rock no neighbour has opened has no face of its own either.
- **The opening column falls whole.** Only then is the opening something a body stands in, with the eye level with the face. A feet cell beside a head that is still standing — the gap under a step — leaves a one-high slot.
- **The column needs no groundwork**, the chain's own condition.

What the offer does not reach is a cell whose way in is not the next column: the rest of a first row the ramp runs along, or a cell walled in along its row by bedrock or the blacklist. Those still come on the back pass.

**Missing steps are rebuilt, and there are two ways one goes missing.** A cave took it — the case this was asked for, and the bot has to walk *through* that cave to get out, so an empty ring cell there is a two-block climb the mesh cannot make. Or the descent took it: `tickDescend` digs through whatever is holding the bot up, and sometimes that is a ring column. Nothing can make the bot take a sideways pace before dropping, so the descent is allowed to break a step and `repairStairs` puts it back.

That is why the repair runs **during** the sweep rather than at the end of it. At the end of a slab a step the descent dug has lost every neighbour — the whole slab is air — and `findSupport` has nothing to offer. During the sweep the foot-layer step's support is the cell below it, still solid until the next slab, which is reliable; a head-layer step depends on a horizontal neighbour still standing and is best-effort. The sweep's first column also moves the bot off the cell it landed in, so the step it was standing on goes back in on the next call — early, while the slab is still being cleared, so a run stopped halfway leaves a ramp that can be climbed.

`STAIR_REPAIR_LOOKBACK` (4) is the window, and the bound is the known limit of the mechanism: a step further up than that is out of reach from the slab floor with nothing to stand on in between. Four rather than two covers the one cell the repair legitimately declines — a step inside the bot's own body, skipped rather than failed, which is then two layers above the next slab's floor and still in view. A cave up to a slab tall is therefore mended; a taller void leaves the ramp broken, and what reports *that* is the restock's own walk failing rather than a guess made here.

**A step that cannot be built is skipped, not fatal** — unlike a floor. A floor is placed because the bot is about to walk somewhere it would otherwise fall; a step is the way out of a hole the bot is not in yet, and failing on the spot would turn every cave that happens to cross the chunk's edge into a dead run. In a cave the step's every neighbour is gone: the cell below is in range and mined, the ring cells beside it too, and the one face normally there — the chunk wall outside — is what the cave took. Both refusals (no support, no filler carried) warn **once** and carry on. A step that *is* attempted is held to the same bar as every other placement: it goes through `verifyPlacement`, and one that keeps failing ends the run, because then the bot is digging itself into a pit it has been unable to leave a way out of.

### The way out reaches the ground (`EXIT`)

The ramp starts at the floor of the run's top slab, and that floor is only level with the ground outside if the run was started on level ground. Started in a hollow, a dug pocket or against a hillside, the pit's rim sits under a sheer wall up to the ground around the chunk — more than the three blocks a mesh edge drops, more than the one it climbs — and the staircase ends in it. Reported from a real run: started with the feet at y=102, the ground round the chunk at 107 to 111, every walk back from a restock ending in `no way towards …` (the bridges over the shaft in the pathfinding module's *A bridge needs a far rim* were the same trip). A `STAIRCASE` exit has the same wall in the other direction.

So once a run's top slab is done — and only for a run that goes below it — the miner looks for the way out once (`findExitTop`): from the run's top step upward, the first layer whose step has, just outside the chunk beside it (`SpiralStairs.outward`, two directions at a corner), room to stand under the open sky with ground at most three blocks down. Rock there, or a cave or an overhang, is wall the ramp climbs past; open sky with no ground under it — a cliff, or the pit of a chunk mined next door — is nothing a staircase gets onto, and nothing gets built. Once the ramp has had to climb, the ground also has to be no lower than the run's top floor: the climb is for ground that rises over the rim, and the first version, run against the rim-slot fixture (two blocks of rock outside the corner, open margin below), climbed a layer, built a step into the top slab for a drop back below the floor, and cost that test its run. On level ground the answer is the run's own top step and the phase does nothing: the cells over it are the top slab, already mined. After the top slab rather than before, because the pocket a run starts in can be a hole with no way out to the ring until that slab is open.

The phase then works from the bottom up, one layer per batch, because the bot climbs what it has built to reach the next one: the step, placed against the wall when it is air, then the cells over it, three where the ramp is climbed and two on the top step, which is only walked off. The pass covers every layer between the run's top step and the exit, so a run started further down the shaft mends the ramp above it too — including steps from before the ramp was pinned to the height grid. Steps it puts into the top slab are kept there by `isStep`'s already-standing clause, steps above the range are never touched by the sweep. Nothing is fatal before it is tried (no support, no filler, liquid in the way, a block that may not be mined, the bot standing in the cell: the way out stops short with a warning and the run goes on); what is tried goes through `verifyPlacement` and `verifyPlannedBlocks` like everything else.

**Coming back down.** The phase leaves the bot up on the staircase, and the descent digs through whatever holds the bot up — the staircase. So when the bot is still above the top floor, the descent first mines the block of the next layer down nearest to where the bot stood before it went up, at least `WAY_DOWN_MARGIN` (3) columns in from the edge (`wayBackDown`): the walk there brings it down the stairs and off them, and the block is the next slab's work anyway.

### Deliberate slips

Two of the bot module's blunders (`HumanBehavior.blunder`, off while the test fixtures suppress them) are the chunk miner's own. Both are mistakes a person digging makes and puts right, and both happen only where they can be put right:

- **One too deep** (`chunkMinerOverdigChance`, per column): the floor block under a column comes out with it and goes straight back in, through the groundwork that fills a hole under a column anyway. Only while the bot works from the slab floor, only for a block that is diggable work of the next layer down (inside the range, not a step), with sturdy ground under it for the filler, no liquid touching it, and filler carried (`canOverdig`).
- **A step knocked out** (`chunkMinerStairSlipChance`, per planned batch): once the batch is done, a step of the current slab is mined and `repairStairs` builds it back. Only a step low enough to be owed whether it stands or not — the top two layers of a range carry none — in reach and in sight from where the bot stands (a slip it has to walk for is no slip, and one that fails to break fails the run), clear of the bot's body, with filler, and with a face to build it back against that faces the eye by at least `SLIP_FACE_CLEARANCE` (0.2) — from the row beside the step the only support can be the block next to it, whose face toward the step then points away, and the rebuild stared at that block's side until its look timed out twice and the run ended (`slipCandidate`).

**Put back only once the server has had its say** (`putBack`). Both slips place into the cell they have just broken, and the client turns a block to air on its own prediction. The first version rebuilt the step on the tick the sweep saw that air, and a debug trace caught the step as client air against server stone at exactly that moment: the server had refused the break as early and let it run on as a delayed destroy, so the placement met stone and failed, the stone came apart a moment later by itself, and the run finished with a gap in the stair — `verifyPlacement` had passed, because the client still showed a block when it looked. The sweep now holds after either slip until the plan is empty, the controller idle and every prediction settled (`ServerBlockSync`), bounded by `PUT_BACK_WAIT_TICKS` (40) for a connection that never acks. Nothing else is planned meanwhile, so no column can take the block a step is rebuilt against.

### Restocking (`chunkMinerRestock`)

The chunk miner is the first behavior to declare a `RestockNeeds` manifest (see the bot module's *Restocking*), and it may, because it already resumes by reading the world — which is the one condition for opting in, given that suspend is `abort()` and resume is `start()`.

The manifest is a pickaxe, a **shovel**, `FILLER_TARGET` (64) filler blocks, `MEAL_TARGET` (16) meals, and `chunkMinerMinFreeSlots` free slots. A stack of filler rather than more, because a cap, a dam or a bridged floor is one block at a time and a chunk rarely needs dozens — a second stack would only mean more of the inventory unavailable for what is being mined. Everything else the bot is carrying is loot by complement and goes into the chest; the manifest protects the tools by name, so the hotbar is fair game. `isMeal` is the bot module's own predicate, public for exactly this: what the bot will actually eat is one question and wants one answer.

**`chunkMinerRestock` defaults to `true`**, and it is safe to because of the other half of the pairing: an unconfigured server has no storage, so `BehaviorRunner` warns once and the run carries on instead of failing (the bot module's *A shortfall nobody can serve is not a reason to stop*). The two must not be loosened separately — flipping this on is only safe while the server defaults stay tame, and making the server defaults useful is only safe while nothing fails on an unserved trip.

`policy()` keeps `withInventoryFullStop(chunkMinerMinFreeSlots)` **unconditionally**, restock or no restock, and deliberately so: the runner asks the restock before that guard, so one threshold serves both "go to a chest" and "stop, there is no chest". A conditional policy was the first attempt and was reverted — it put the same number in two places and made the behavior responsible for knowing whether a trip was possible.

### Policy

Unlike the diamond miner, the chunk miner opts into **every** guard the bot module's policy layer offers: stop on damage, stop on a player's swing, stop when the inventory is nearly full, plus opportunistic collection, the fast collect exit, collecting while mining (`collectWhileMining`), and a meal between two columns once the food bar is under the bot's `eatBelowFoodLevel` (`autoEat`). It runs unattended for a long time somewhere the supervising player is not watching, so damage means something found the bot, a full inventory means everything mined from then on is lost, and an empty food bar means no regeneration for as long as nobody looks. The two collection flags are what keep the drops arriving without the run crawling. The diamond miner stays without any of it — it is not in use and, as of this writing, broken in other ways.

### Collecting while mining (`collectWhileMining`)

Even with the top-up (see *Why the collect round is hard to remove*), the queue still emptied between batches and the controller collected to completion before the next block — the bot stood still until a drop that had rolled aside was in its inventory, which reads as a machine. Under `BotPolicy.withCollectWhileMining` a break goes straight on: the next queued block, or idle for the sweep to plan one. Drops come in through the opportunistic step during the next break and vanilla pickup on the way.

What nobody walked past is swept once per slab: when `nextColumn` has nothing left, `tickClear` hands the controller the slab's own box (`BotController.sweepDrops`, one block below the floor to the top of the head layer, the whole chunk) and waits until COLLECTING is over before SELECT_SLAB, which is also where a run ends — so a finished run has its ground clear. `slabSwept` keeps it to once per slab. Pinned by `mines on with drops lying about`: two sticks off to the side of a four-column corridor, failing if COLLECTING ever runs while a corridor block still stands, and then demanding every cobblestone and both sticks.

### Safety

- **Never outside the chunk.** Nothing is mined outside it, and nothing is placed outside it either — with one exception: a water source just beyond the border that would otherwise refill the chunk as fast as it is dug.
- **Never a fall.** In `DESCEND` the drop below the cell about to be opened is measured, and anything deeper than two blocks gets a filler placed first. In `CLEAR` the floor under a column is filled the other way round — **after** the column comes out, never before it: while the column stands it is the roof over that cell, so no face of it can be reached from anywhere the bot can stand, and `findSupport` hands back the column's own underside, which a ray from the side never meets. Filling it first therefore burned three look timeouts and killed the run on a hole it had no line to. The column is mined, the fill goes in through the opening it leaves (the same mechanism walled-in water already used), and the sweep chains no further column while a floor is owed. What keeps the bot out of the hole in between is the controller: `POSITIONING` refuses a step with no ground under it, the way `COLLECTING` already did — before that it walked into the cavity in a straight line and arrived at the bottom (measured: a four-block fall, `Bot refuses to walk off a ledge`). Over a cave the cell to fill has lost every neighbour but the block the bot is standing on, whose side face its own footing hides; the controller bridges that one, crouching out past the rim to click the face (see the bot module's *Bridging*). A support on the *far* rim of a wide cavity is a different matter — out of reach, and bridging reaches one block — so that still stops the run.
- **A gap on the way is bridged, not stared at.** The refusal above is right and it is not the whole answer: it also fires on the walk to a column that is merely out of reach, and there standing still is a dead end. Measured in a real world at y=92..93 — two columns mined from 3.6 and 3.8 blocks away without a step, the next at 4.77, then six tasks that each ended where they began (`player=(-22.23, 92.00, -62.00)`, `pathActive=false crouched=false under=stone`) and `cannot break -27, 93, -61`. Nothing was wrong with the aim; the bot simply could not walk there and nobody filled the cell. `ensureStepToward` does it before the mine task is handed over, one cell at a time — the sweep re-reads the world every tick, so no route is remembered. It walks **the line the bot will actually walk** — a grid traversal from the bot's own cell to the column, one axis at a time so that each cell is orthogonally next to the last and a placement always has a face to build against. Neither walk that gets the bot there pathfinds: `POSITIONING` and `COLLECTING` both hold the walk key in view direction, so the way to a column is the straight line and nothing else. Sampling an L instead — the whole of one axis, then the other — asks about the cells round the outside of that line and never about the diagonal ones on it, and the bot stood still in front of a cell nobody had looked at while the sweep reported the way clear (`retrying -29, 93, -61 — nothing to mend on the way there`, the L's row solid the whole way, `-26, 91, -62` open and on the line). Five things make it safe, and each of them was learned by getting it wrong first:
  - **Built from underfoot, never from the far rim.** `ensureFloor` leaves the support to `findSupport`, which ranks faces by how squarely they face the eye — across a gap that picks the neighbour on the *other* side, and the bot then walks round to a face it can see, into the hole it was bridging (`filling the floor at -24, 91, -61` against `-24, 91, -60`, from a real world). Bridging pins the support instead: the block underfoot, or the last one laid. That support is always horizontal and below the eye, so `needsEdgeStep` holds for every cell of a bridge and the bot is **crouched the whole way out** — it cannot walk off, which is the property the technique is for.
  - **Slab level, not "within one block".** `isSturdyFloor` demands floor at `slabFeetY - 1` and nothing lower. Borrowing the controller's `hasFloorWithinOneBlock` looks right and is not: it tolerates a one-block drop because it is answering whether a step is survivable. The sweep is answering whether a cell is the floor it works from, and the bot duly walked down into a dip and placed its next block beside its own head.
  - **Only while standing on the slab, and never as far as the column.** Off the slab the sweep's geometry does not hold, so it builds nothing. And a hole *under* the column is the case above — filling it from here would be that ordering bug again. Both fall out of the bounds rather than needing a special case: the walk stops at the cell *beside* the column and never names the column's own.
  - **Beside the column, not within reach of it.** Reach is what the break needs; what falls out of the break needs a bot that can walk to where it lands, and `COLLECTING` has no pathfinder to go round with — it walks the same straight line and stops where the line stops. Stopping the walk at reach let the bot mine a whole wall from one cell of bridge and abandon every drop of it on the far side of the gap it had just declined to fill: the run then burns the collect no-progress budget on every column, which is what the user saw as a bot that bridges beautifully and brings nothing home. Reach and footing are two different questions; only one of them is the one the sweep is asking.
  - **Asked twice: once on a guess, once on a fact.** All of the above runs on the tick a column is planned, which means it is predicting a walk that has not happened yet — and it used to get exactly one attempt, because `verifyPlannedBlocks` re-queues a failed break without going back through the sweep. A single miss then ended the run: three identical retries and `cannot break -27, 93, -61 (blocks mined: 0)`, six position timeouts at one unchanging spot, with solid ground under the bot and an open cell one step west of it. So the retry asks again, and there it is not predicting anything: the approach has failed, which is a fact, and the bot is at rest on the ground where the attempt left it. The same question answered from there mends the floor and the run goes on; when it cannot, it now says so in a line instead of declining in silence, which is what made the original report so expensive to read. Both halves are load-bearing, measured by switching the preemptive check off: the timeout case survives on the retry alone (`bridging the floor at 3014, 39, 3015` after two `Could not get within reach`), while the dip test dies — a dip produces no timeout at all, because the walk *succeeds*, into the dip. Two disjoint failures; neither mechanism covers the other's.
- **Bedrock and blacklist** are skipped, never fatal. Bedrock is unconditional and does not belong on the blacklist — it is not a preference.
- **Water** is flood-filled up to `FLOOD_FILL_LIMIT` (128). A single source on a flat floor spreads into a diamond of 113 cells, so a pool of one or two sources is surveyed whole, sources included; the cap was 16 for a long time, which no spread pool ever fit under, so none was surveyed whole and every one was dammed cell by cell across its flowing edge. A surveyed pool with up to `MAX_SEALABLE_SOURCES` (16) has **only its sources** capped, which leaves the chunk dry for good — the spread drains by itself once they are gone, and a block on a flowing cell is a block for nothing. Flowing water with no source anywhere in it is what a capped pool leaves behind; it is waited out standing still (`RESIDUAL_WATER_TICKS`, 100 — water recedes a level per fluid tick, five ticks apart) and dammed only if it is still there, fed from somewhere the survey did not reach. Anything bigger is dammed at the face it would flow in through (`damAcross`). One placement per call, and a cell with nothing to build against yet is passed over for one that has — a source in the middle of a pool has only water round it until its neighbours are capped, and failing on the first such cell ended runs the next placement would have made possible.
- **Lava is always dammed.** Waiting for it to turn to obsidian costs far more time than a block of cobble.
- A filler placement is verified like a break and is **fatal** when it keeps failing — it was planned because the bot could not safely proceed without it.

## Commands (`/miner`)

| Command | Description |
|---------|-------------|
| `/miner diamond start [tunnelLength]` | Start the diamond miner (default length from config) |
| `/miner chunk start [fromY] [toY]` | Mine out the chunk the player stands in; no arguments means from the layer pair the player stands in (feet and head) down to `chunkMinerBottomY` |
| `/miner chunk blacklist add\|remove <block>` | Edit the blacklist; a bare name is accepted and `minecraft:` filled in |
| `/miner chunk blacklist list\|clear` | Show or empty the blacklist |
| `/miner stop` | Stop the behavior (equivalent to the behavior part of `/bot stop`) |
| `/miner status` | Show the active behavior status line |

The blacklist is also a page in the gui module (`/gui chunk_blacklist`, or the root menu), with an "add the block you're looking at" button. That reads `Minecraft.hitResult`, which still holds whatever the crosshair was on when the menu opened — a block-selection mode with no click handling of its own and no mode the player can get stuck in. The screen itself is the gui module's `IdListScreen`, shared with the bot's ignored-items page; `BlacklistPage` supplies only the wording, the id check (`MinerCommands.normalize`) and that lookup.

The chunk miner's two plain knobs are a second page (`/gui chunk_miner`), on the gui module's shared `SettingsScreen`: `chunkMinerRestock` as an on/off row and `chunkMinerMinFreeSlots` cycling through `{1, 2, 3, 4, 6}`. A hand-edited value outside those steps is not rejected — the next click simply lands on the second step, because a menu that refuses to move is worse than one that snaps to a sensible value. A slider would need the screen to know the setting is a number; cycling is what the one row type already does (see the gui module's *Shared screens*).

The `add`/`remove` arguments are `IdentifierArgument`s, not strings: Brigadier's unquoted string stops at the colon, so `minecraft:chest` parsed as `minecraft` with `:chest` left over and the command failed on exactly the ids its own tab completion offers (measured against brigadier 1.3.10). A bare `chest` is still accepted — the argument fills the namespace in.

## Config

Persisted to `stracciatella/miner.json`:

- `floorOffsetAboveBedrock` — tunnel feet height above the highest bedrock in the start column (default 3)
- `defaultTunnelLength` — tunnel length when `/miner diamond start` has no argument (default 32)
- `oreScanRadius` — diamond scan radius around the player (default 4 ≈ mining reach, so found ore never requires navigation away from the tunnel)
- `maxStepRetries` — re-enqueues per step before giving up (default 2)
- `chunkMinerBlacklist` — block ids the chunk miner leaves standing. **Ids only, no block states**: a blacklist the player edits by name is worth more than one that can tell a facing apart, and no realistic entry needs the distinction.
- `fillerBlocks` — what the chunk miner places to seal or dam, in order of preference; the first one it actually carries is used
- `chunkMinerBottomY` — lowest layer for an argument-less `/miner chunk start` (default -59, the first layer that is never bedrock in a vanilla overworld; clamped to the world floor). Only the bottom is configured — the top of an argument-less range always comes from the bot, and `resumes the layer it stands in` pins this one so that run has an end.
- `chunkMinerMinFreeSlots` — the run stops below this many empty slots (default 2)
- `chunkMinerOverdigChance` / `chunkMinerStairSlipChance` — the two deliberate slips, per column and per planned batch (defaults 0.01 / 0.005; 0 switches one off); see *Deliberate slips*
- `chunkMinerRestock` — whether a shortfall sends the bot to a chest instead of ending the run (default **true**). Safe as a default only because an unconfigured server has no storage and an unserved trip warns once rather than failing; see *Restocking* above and the bot module's tame `servers.json` defaults. The two halves of that pairing must not be loosened separately.

## Testing

`./gradlew runMinecraftTests -Psuites=miner,chunk` for the in-game suites, `./gradlew :modules:miner:test` for the unit tests.

**Miner Tests** (not registered in `MinerSetup` for now: the diamond miner is unused and broken in real worlds, and the suite comes back with that one line when the behavior is picked up again) build a deterministic deep-mining sandbox (bedrock floor at -64, solid deepslate above, air on top):

- **Miner tunnels at depth** — player starts in a pocket at tunnel height; tunnel 5 slices, one ore in the path; expects 1 diamond and a fully dug tunnel.
- **Miner descends and mines diamonds** — player starts 3 levels above tunnel height; staircase descent, 6 slices, one path ore plus one side-wall ore (mined via the ore scan, not the slices); expects 2 diamonds.

**Chunk Miner Tests** run against a chunk that is empty apart from the few blocks each test cares about. The behavior skips columns with nothing to dig, so a sparse chunk exercises the same code as a full one in a fraction of the ticks; the layer range is pinned to one slab (two for the descent test) so a run has a defined end instead of eating its way to bedrock. **`resumes the layer it stands in` is the one exception** — it requests no range at all, because deriving the range from the bot is exactly what it tests; only `chunkMinerBottomY` is pinned, to give the run an end. Covers: clearing a slab, blacklist, bedrock, the chunk boundary, descending, capping a water source, damming lava, a corridor, mining on past drops lying beside it, the staircase being left standing and mended, a cell the staircase walls in, one it only opens a rim slot to, one only its top face opens, one taken with the column that opens it, the ramp surviving a run restarted lower, both deliberate slips put right, the way out reaching the ground the run started below, and three that measure the run rather than its result.

The fixture (`prepareWithFloor`) suppresses the bot module's blunders, so no test meets a slip it did not ask for. `digs one too deep and puts the floor back` and `knocks out a step and puts it back` switch them on for themselves with the chance at 1 (`withSlips`, everything restored in a `finally`), three repeats each. The first lays ground under the fixture floor and stops once the overdug cell is cobblestone again, since a range reaching the floor layer would go on to dig the whole floor for real; it asserts the dig, the refill and that the feet never went below the floor. The second runs on the staircase fixture, where every column of the lower slab is followed by a slip, and counts the times a step went from standing to air — the lower step once anyway, dug by the descent — then asserts both steps standing and the rest of the fixture mined. Its runs found both conditions the slip has now: the race behind *Put back only once the server has had its say* (`the staircase's top step … was mined but should have survived`), and, once that was fixed, the support facing away (`could not place the step at 3008, 60, 3008 — 2 attempts failed`, two of three repeats, from a bot standing at z=3009.24 against a face at z=3009).

`builds its way out up to the ground` is the pit a real run left, rebuilt: a hill against the east edge six blocks over the run's top floor, twice what a mesh edge drops, on a two-slab range. The ramp's two steps in the top slab are air and have to be built against the hill, the four above the range stand in ground the way out digs through — the last of it out of reach from the floor, so the bot climbs what it built and then has to come back down before the descent. The lower slab's step is set up standing, as rock would be, so the test is about the way out and not about the repair. It asserts the steps standing and then what a restock needs: a journey from the hill top, placement off, arrives on the pit floor. Without the way out that journey has nowhere to go — the top step is six below the hill. Three repeats, because the bot's path through the headroom work varies from run to run, and the four controller fixes it needed each showed up in only some of them: the body standing in the cell a step was placed into (bot module, *No block goes where the body is*), a block high over the floor worked from the floor instead of from the stairs (the standoff search in *Key integration points*), the place to stand picked on top of the pillar of ground beside the block, where no path leads (the same section: the walk now goes to the best place a path reaches), and the walk during a break parking the bot under the column it was digging upward (*Nor a block over the head*). The slip test's repeats found another along the way, the placement approach crossing behind the face it builds off (*A side face at eye height or above is approached from in front*).

Those three — **mines without stalling**, **resumes the layer it stands in**, **holds its aim** — exist because the other eight cannot fail on a bot that breaks one block, stares at a wall for a thousand ticks and breaks the next. `TestRunner` multiplies `timeoutTicks` by the tick multiplier, so the corridor test's nominal 3000 ticks is a 30000-tick budget for eight blocks. They therefore carry **their own budget** in game ticks, `blocks * TICK_BUDGET_PER_BLOCK` passed to `waitFor`, and sample the tick thread once per tick through the `waitFor` predicate (which is evaluated there anyway — per-tick *logging* perturbs the corridor test enough to flip it, so the sampler stays field arithmetic).

Two sensors, because looking busy and making progress are different questions. `getDestroyStage()` is `destroyProgress > 0 ? (int)(progress * 10) : -1` with **no `isDestroying` guard**, so it is exactly "a block is losing hardness this tick" — the duty cycle. `player.swinging` is "the button is held" — the swing `BlockInteractor` mirrors from `Minecraft.continueAttack`, which is the thing that went missing in the regression that started this work and which progress alone would not notice.

`MultiPlayerGameMode.isDestroying()` reads like the obvious sensor and is useless: measured over 482 ticks of a passing run it was never once set. `handleKeybinds` calls `continueAttack(false)` every tick — no key is down in a test client — which calls `stopDestroyBlock` and clears the flag, and only `startDestroyBlock` ever sets it, never `continueDestroyBlock`. It survives one tick per block.

The gap between the two is the finding: **79% swinging against 25% breaking.** `continueDestroyBlock` returns true, and so the bot swings, while `destroyDelay` is draining — vanilla sets that to 5 the moment a block completes (bytecode offsets 5-22 for the early-out, 368 for the assignment), and `MultiPlayerGameMode.tick` never decrements it, so it only drains while something keeps calling that method. A player holding the button drains it while moving the mouse to the next block; a bot that stops calling it in order to aim pays all five serially, on every block.

**The thresholds are targets, not calibrations, and the miner does not meet them.** An earlier revision set them from what the miner happened to do, which made the suite certify the slowness it was written to expose — a bar drawn round the implementation can only ever agree with it.

The budget now comes from a person doing the job by hand: **16 stone blocks with a pickaxe in 10 seconds**, so 200 ticks, and the test allows 220 for that work — `blocks * 220 / 16`, or 13.75 ticks per block. A human reference settles what the game actually permits, and it corroborates the arithmetic: 16 blocks is 96 ticks of pure breaking at `8/1.5/30`, so the remaining 104 are overhead nobody escapes — essentially the 5-tick `destroyDelay`, paid *during* the mouse travel rather than after it. The rest of the bars: 40% duty (real progress, which is about what a person hits), 90% swing (the button is held), 45 degrees of yaw per block (one aim per column, one turn per row), a 35-tick gap ceiling (the longest pause the design sanctions — a 25-tick breather plus a 10-tick reaction), and 90% of drops collected ("very rare break").

**Measure the pace at `-PtickSpeed=1`, not at the default 10.** The two costs that dominate a break are server round trips — the block-change ack that ends INTERACTING, and the item-entity sync that ends COLLECTING — and a round trip costs constant *wall-clock* time. At 200 tps a tick is 5 ms, so the same latency counts ten times over in ticks. Measured directly: the trace's `tail` (ticks in INTERACTING after the last tick of real hardness progress) is **6.8 per block at 10x and 1.0 at 1x**, and the `BREAKEXIT` instrumentation showed `seq=20 acked=19` for five straight ticks before the ack landed. A budget stated in game ticks and compared against a human benchmark recorded at 20 tps is therefore ~6 ticks per block stricter at 10x than the requirement asks. The tests are left running at whatever the suite uses and the budget is unchanged — the miner misses it at both rates, so there was nothing to fix in the measurement — but any pace figure quoted without its tick rate is meaningless.

The breakdown that located the problem, over a 248-tick two-slab corridor run of 13 blocks at 1x, **19.1 ticks per block** — before the queue top-up below:

| per block | ticks | reducible |
|---|---|---|
| breaking (real progress) | 5.0 | no — `8/1.5/30` is a game constant |
| lead: entering INTERACTING to first progress | 3.2 | barely — one tick of hook ordering, one of `startDestroyBlock`, the rest residual `destroyDelay` |
| tail: break confirmation | 1.3 | no — this is the ack, already the fast path |
| LOOKING | 3.5 | partly — humanisation lives here |
| **COLLECTING** | **5.5** | **this is the whole remaining gap** |
| IDLE (replanning, breather) | 0.5 | partly |

The pickaxe, the tool choice and the ground contact are all fine (`held=diamond_pickaxe`, `air=0`), and the break runs at exactly the speed the game allows. Subtract COLLECTING and IDLE and the loop lands at 13.5 — essentially the 13.75 budget. **The pace problem is now entirely the collect round**, and the reason it is hard is below.

### Why the collect round is hard to remove

`continueSeam` — the path that skips both the collect and the reaction beat — is taken only when a task is **already queued at the tick a break confirms**. `tickClear` used to plan exactly one column (2 blocks), so the queue was empty at every second block and the collect round was guaranteed: 5.3 ticks per block of COLLECTING plus 1.8 idle, against 5.0 of actual breaking.

Chaining several columns into one plan fixes the within-batch case, and the chain is bounded by **vanilla's pickup box (1.425 blocks), not by reach**. Reach (4.0) was measured and is worse: the bot clears everything it can touch from one standing spot and then walks back over four blocks of loot. It bought 4.1 ticks per block of COLLECTING and gave back 24 ticks of SCANNING and POSITIONING plus a 40-tick break in the mining — the aim test counted a long gap that had not been there, and continuous mining is the requirement. Columns needing groundwork (a cap, a dam, a floor) are never chained: `planPlacement` clears the plan, and the intervention has to run *before* the cell in front of it opens.

**Topping the queue up mid-break is what removes the collect round, and it needs two things to be safe.** Between batches the queue still empties, so the behaviour plans while the controller is still in INTERACTING (its `tick` gate otherwise refuses unless the controller is idle or collecting), with `verifyPlannedBlocks` leaving the in-flight block alone — that block has not failed to break, it has not finished being tried, so it neither counts as a failure nor goes back into the queue when another block of the batch did fail (a retry that re-queued it put a second task behind the first, and that one stared at the emptied cell for two look timeouts) — and `plan` appending instead of replacing.

1. **`BotPolicy.withOrderedTasks`.** Without it this change is a catastrophe, not an improvement: handed a choice mid-break, `pollNearest` takes a block behind the column still standing in front of the bot, the hit-result gate never fires, and the task burns a look timeout and a re-approach. Measured: the corridor test failed outright (`cannot break 3019, 41, 3015`) and `mines without stalling` fell from **19.1 to 62.0** ticks per block, 136 of 248 ticks in LOOKING.
2. **The same pickup-box bound as the chain.** Planning mid-break for a column further than `CHAIN_DISTANCE` mines a block whose cobble lands where the bot is not standing, and nothing comes back for it — the collect round being skipped is the thing that would have. Unbounded it cost five of fifteen drops, and the corridor test timed out with all eight blocks mined and the cobblestone still on the floor. Bounded, the bot collects, walks, and plans again from where it lands.

Groundwork keeps its own guard on the same path: `planPlacement` clears the plan, so a cap, a dam or a floor must not be started while a block is still under the pick.

Together with the bot module's pre-aim during the break confirmation, the whole loop at 1x looks like this, against 19.1 before — **13.8 ticks per block, 20 of 20 blocks, 19 of them collected**:

| per block | ticks | against 19.1 |
|---|---|---|
| breaking (real progress) | 5.0 | unchanged — `8/1.5/30` is a game constant |
| lead: entering INTERACTING to first progress | 4.4 | up from 3.2 |
| tail: break confirmation | 1.5 | unchanged |
| LOOKING | 1.5 | down from 3.5 (pre-aim) |
| COLLECTING | 0.6 | down from 5.5 (chaining + top-up) |
| IDLE | 0.8 | unchanged |

The collect round is gone and the aim is nearly free. What is left over breaking is **vanilla's five-tick `destroyDelay`, and it is a fixed budget, not a cost that can be removed** — it only drains inside a call to `continueDestroyBlock`, so every tick the bot spends confirming, aiming or collecting spends one of the five, and whatever is left is paid at the head of the next break. That is why the lead grew as LOOKING shrank: the same five ticks, moved. A human pays them too — 16 stone in 200 ticks is 12.5 per block against a floor of 6 breaking plus 5 delay. Chasing the remaining tick is chasing that floor.

The other two tests at 1x: `resumes the layer it stands in` mines all four blocks with the last break on tick 52 of a 55-tick budget, and `holds its aim` all twenty with the last on tick 270 of 275 — both fail only because the budget has to cover the *run* ending, not just the mining. `mines without stalling` is the laggard at 15.5 (from 20.7): it digs down through its own floor, so it walks between batches and pays a collect round each time.

Falsified against the pre-fix code with the session's three fixes stashed: `duty 0%, swinging=0` fails both the stall and the resume test, while **all eight older tests stayed green** — the measurement that justifies these three existing.

`holds its aim` is a coarse guard, not a regression test for column ordering, and its javadoc says so. Two geometries were measured against the ping-pong scan: a ring of eight columns costs a full turn in any order (61 deg/block on both broken and fixed), and a flat patch reaching three columns either side gives 98 broken against 81-92 fixed — overlapping ranges at an 11% run-to-run spread, so no threshold separates them. It does not assert the gap or duty thresholds either: with twenty columns in reach its collect pattern differs (56% duty, gaps to 74 ticks).

The corridor test is the only one that is more than one column wide, and that width is the point: with a single column there is never a next column to plan, so the controller collects to completion and the steady-state loop — planning that overlaps collecting — never runs. It digs four columns and asserts the **cobblestone count**, not just that the blocks are gone: everything that makes the loop fast trades against picking the drops up at all, and nothing else in the suite would notice a corridor mined clean with the cobblestone still lying in it. Measured at the COLLECTING exit gate: the first two columns take 10 and 11 ticks with a real collect, the last two leave on tick 1 because vanilla pickup already inhaled the drop during the break, and every exit reports clear ground.

This test is **timing-marginal at accelerated tick rates** and is the first thing to look at after any change to the collect path. It depends on the drop having synced to the client before COLLECTING decides, so anything that adds client work per tick can flip it — it flipped on a single per-tick particle spawn in `BlockInteractor`, and only in the full 187-test run; the module suites stayed green throughout. A single failure is not proof of a regression on its own: re-run it alone, and compare against a baseline run with the change stashed. Observed rate across eight archived runs: five green, three red.

The first root cause was the *success condition*, not the mining: a run could end with drops still on the ground, and `awaitChunkMiner` stops the bot before the corridor test starts waiting, so its 1200-tick wait for 8 of 8 cobblestone could only be satisfied by luck. That one is gone — the miner now sweeps every slab before it moves on or reports success (*Collecting while mining*, below).

The second is the **fixture**, and the sweep cannot fix it: `prepare` lays its floor flush with the corridor's last column (chunk-local x 11), and a drop pops up to a block sideways, so one from that column can go over the edge into the cleared volume four blocks below — out of every collect walk's reach. Logged at the sweep's start: a cobblestone at x=3020.45 against a floor ending at 3020, gone from the slab ten ticks later, seven cobblestone in the inventory and one killed by the next test's `kill @e[type=item]`. Both corridor tests (`clears a corridor`, `mines on with drops lying about`) therefore lay their floor two blocks past the last column; the bar, 8 of 8 cobblestone, is unchanged.

The water-cap and lava-dam tests place their source and start the run inside a `tick freeze` / `tick unfreeze` bracket, with one cleared corridor cell between bot and liquid. Setup commands are wall-clock bound while the world runs at ten times speed, so an unfrozen gap is worth hundreds of fluid ticks — enough for the lava to reach the bot before its first tick, and for a pool to outgrow the flood-fill cap that decides capping against damming.

The spread-pool test (`caps a spread pool at its source`) is built differently: one source given time to spread into its full diamond, and the bot on a one-block pedestal in the middle of it — its own column, which the descent digs through, so the pool is what that column touches, the way a run meets a pool from inside it. The pedestal is what keeps the bot dry and where it is: flowing water carries a player off at about a third of a block a second, and a bot that has drifted out of reach of the source while the world was being built tests the walk, not the cap. Two earlier fixtures did not survive being ray-traced against the code: a one-high rim at slab level hides the whole floor under the pool from an eye outside it (`hasLineOfSight` clips eye to block centre against the outline shapes with fluids ignored), and stepping onto the rim risks walking into the pool. Every filler block that ever stands in the pool has to be the cap on the source; a block on a flowing cell at any point of the run — in the first plan, or after the cap while the spread is still draining — fails it. The gravel test (`mines the gravel that falls into a column`) stacks two gravel on a column's head block and asserts the whole column, gravel included, air at the end of a run that did not fail; the fallen block is the mine task's next sub-target (the bot module's *Falling blocks*), not a step retry. The sourceless-water test (`waits out sourceless water`) reuses the spread-pool fixture and takes the source away under `tick freeze` before the run: the whole spread with nothing feeding it, and not one filler may stand in it — the residual wait (`RESIDUAL_WATER_TICKS`) is what keeps the dam off, and it says so in the log once per column, the way a cap or a dam does. The blacklist command test (`blacklist commands edit the list`) runs `/miner chunk blacklist` end to end, namespaced id included, against a list that is set aside and restored, file included.

The staircase test (`leaves a staircase and mends it`) needs a fixture that can tell "rebuilt" from "never mined", and the first two attempts could not. Pre-clearing a step and surrounding it with standing stone makes it occluded and unreachable, so nothing could have placed it either way; a three-slab range made the second descent's column non-deterministic, and with it the identity of the step the descent happens to break. What works is a **two-slab** range with the bot starting on chunk-local `(1, 0)`, whose foot-layer cell *is* that layer's step: the descent is then forced to break a known step, and the assertion is that the cell holds **cobblestone** rather than merely that it is not air — cobblestone is the filler the bot was given, so only a placement can have put it there. The test also asserts the ramp's top step is still standing and that every other cell in the range is air, which is what catches an exclusion that excludes too much.

Falsified twice, in the two places it has to be: with the `isMinable` exclusion removed the run dies with `could not place the step at 3008, 39, 3008` (the sweep mines the ramp, then the repair tries to rebuild a step in the cell it is standing in), and with the `repairStairs` call removed it fails with `was not rebuilt: found air, expected cobblestone`.

**The three staircase fixtures run at `STAIR_Y`, not `Y`**, and that is not a preference either. All three are built around the chunk's *minimum corner* — the one cell with two faces pointing out of the chunk, which is the whole subject of the other two — so they need a fixture whose floor layer is the layer that owes its step there. Now that the ramp is pinned to the world's height grid that is a fact about the height and nothing else: at `Y` = 40 the steps for those layers sit on the east edge instead, outside an 8×2 fixture and therefore in air, and the repair goes chasing them (`the step at 3023, 40, 3013 is missing`). `STAIR_Y` is derived rather than written down — the first height at or above `Y` whose floor layer is a corner layer — so it follows the geometry if the ramp is ever re-pinned.

`keeps the staircase when a run starts again lower` is the fourth of the family and the one the reported bug is named after. Two starts, both **argument-less**, because that is the only shape the bug had: a requested range fixes `fromY` and two runs then agree by accident. The second stands the bot two layers down, the way a person restarting a stopped run does — and the way a restock resume does — and its slab covers both layers the first run left steps in. Only the bottom of the range is pinned, as in `resumes the layer it stands in`: the top is the variable under test.

`finishes past a cell its staircase walls in` is its companion, for the cell *under* a step. It walls that cell in for good — the two outward faces get stone placed **outside** the chunk (never this run's work) and the inward one gets **bedrock** (never diggable) — because the permanently sealed case is the one that cannot resolve itself as the sweep goes past, and therefore the one that has to end the slab rather than the run. The bot stands on chunk-local `(4, 1)`, deliberately *off* the ring: on a ring column the descent digs a step, which would hand the cell an open side for as long as the repair takes. Asserts the run **succeeds**, that the cell is still standing, and that everything the sweep could reach is air. Falsified by making `hasOpenFace` return true: `Chunk miner aborted: cannot break 3008, 38, 3008 (blocks mined: 21)`, the same shape as the report it came from. That the *temporarily* hidden cell still gets mined needs no test of its own — every other fixture here asserts itself completely cleared, so over-deferring shows up as a leftover block in all of them. *When* it gets mined is a different question, and `takes a waiting cell with the column that opens it` asks it.

`waits out a cell only a rim slot opens` is the third of the family and the one that asserts the cell is **not** given up on. Same corner cell, same lid and same step beside it, but the two outward faces are open the way a real rim leaves them: air at the slab's level with stone over it, outside the chunk. Inward it is plain slab stone rather than bedrock, so the sweep is going to take that neighbour anyway and the cell resolves itself — the run succeeds, both steps stand, and the cell ends **air**. The stone over the slot is what makes the fixture falsify rather than decorate it: a two-cell opening would let the bot stand out there and mine the cell, and the run would pass with the rule reverted. It also has to build its rim out of the margin the prepare already clears — `setBlock` waits until the client sees a *non-air* block, so setting a cell to air with it can only time out, which is what a 39981-tick timeout on the first run was. Falsified by letting an out-of-chunk neighbour count as a face again: `Chunk miner aborted: cannot break 3008, 38, 3008 (blocks mined: 21)`, the same shape as the report it came from.

`waits out a cell only its top face opens` is the fifth, for the cell *over* the lower step, and it is built where the report met it rather than at the corner: upper step on chunk-local `(15, 2)`, lower on `(15, 3)`, on the range's second slab, whose snake runs its rows from the south — so the back pass comes east along row 2 and turns into row 3 at that cell. Its head layer is derived from the ring the way `STAIR_Y` is. The bot descends at `(14, 1)`, off the ring, with nothing ahead of it, so the back pass is the first thing that runs; the cell's west and south neighbours are single blocks with air under them, which covers both sides and leaves nothing to climb for an eye over the top. Asserts the run succeeds, the cell and both neighbours end air, and both steps stand. Falsified against the old rule with the report's own diagnostics line for line — `player=(3022.70, 42.00, 3010.70)`, `face=up`, `hitResult=3023, 43, 3010 (west)`, `still standing in the way: 3022, 43, 3011` — ending in `cannot break 3023, 43, 3011 (blocks mined: 1)`.

`takes a waiting cell with the column that opens it` is the sixth, and the only one that asserts **when** a cell falls rather than whether. It uses the same two steps on `(15, 2)` and `(15, 3)`, but on the range's only slab, whose snake runs row 3 from the east, so the cell over the lower step is that row's first column on a forward pass. The bot stands at `(12, 2)` with row 2 otherwise empty, and row 3 stands from `(8, 3)` to `(14, 3)`. A single block south of the cell leaves `(14, 3)` as its only way in, which is where the unmined row 4 put it in the world. The test records the order the head layer comes down in and asserts that the cell falls before `(12, 3)`, with the column that opened it rather than after the row. Falsified against the code without `addColumnBefore`: `[head 14, head 13, head 12, head 11, head 10, head 9, head 8, cell]`.

`aims around the next block at a row turn` is the controller's aim at the turn every row ends in, built as the report stood: the bot inside `(1, 3)` at the logged spot, facing south against row 4, `(0, 4)` a floor block only, `(1, 4)` and `(2, 4)` whole. The head block of `(1, 4)` hides the half of `(0, 4)`'s top face nearer the bot but not its centre, and it is the next task, so the lean toward it put the aim point in exactly the hidden half while the line-of-sight check said clear. The aim jitter is pinned to zero for the run and restored in a `finally`: a draw that cancels the lean lets the old aim through about one run in nine, and this test's first run was one. One column beside the bot, obsidian over stone. Asserts that the obsidian was queued again while the stone was still in INTERACTING — without that the test would pass on a fixture that no longer reaches the case — that no task looked at a cell already empty, and that the run ended on `cannot break` for the obsidian. **SpiralStairsTest** (JUnit, 10 tests) covers the geometry without a game: one step per layer, every step inside the chunk, consecutive steps horizontally adjacent and exactly one block apart vertically, a full circuit landing under its start, and — the one that earns its place — `theTwoDirectionsAgree`, which asserts over a 120-layer range and all 256 columns that `isStairCell` and `ringIndexAt`/`stepAt` answer the same question. The repair reads the ramp in the inverse direction from the sweep ("which cell does layer *y* owe" rather than "is this cell a step"), and two implementations of one geometry that disagree anywhere would have the repair rebuilding cells the sweep then mines. `theRampIsPinnedToTheWorldsHeightGrid` is the one that would have caught the rotating ramp: it nails the anchor to concrete values (`ringIndexAt(0) == 0`, `ringIndexAt(39) == 21`) so re-introducing any run-dependent term fails immediately, and it walks the ramp across **y = 0**, where `floorMod` changes sign — a wrap that sits inside every real shaft, since the default floor is -59 and a chunk started at the surface crosses zero on the way down.

**ChunkMinerSerpentineTest** (JUnit) asserts the column plan visits all 256 columns exactly once, never jumps between non-adjacent columns, and starts each slab where the previous one ended.
