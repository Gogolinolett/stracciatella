# Problem

How are micro-saccades added during sustained aim without breaking the convergence gate?

# Lösung

Decision: CameraController exposes setMicroSaccadesEnabled(boolean). When enabled it injects tiny target perturbations (0.5 deg yaw, 0.3 deg pitch, either way) refreshed every 6-22 ticks (Gaussian, mean 12). The perturbation is excluded from isAimedAt so saccades never break the convergence gate. Alternatives: per-tick offset inside the controller (chosen) pro: the spring-damper absorbs the jitter naturally, one toggle per consumer, no caller code change; contra: adds saccade-state fields to the controller even when unused. Caller computes the saccade and passes it via offsets pro: the controller stays simple; contra: every consumer would duplicate the saccade state machine, and saccades would also affect raycasts because the offset target moves, which matters when callers like the bot already pass jitter offsets for face aim. Random walk on yaw directly between updates pro: no target change needed; contra: fights the spring physics, because every direct write resets velocity and causes a visible jerk. Rationale: the spring-damper is the right place to absorb noise - feeding a perturbed target produces a smoothly tracked perturbation, while writing directly to yaw would always conflict with the spring. Excluding saccades from isAimedAt matters because the bot hit-result gate already validates separately whether the raycast lands on the target, so letting saccades make isAimedAt flicker would cause spurious gate reopens.
