# Problem

A placement is client-predicted just like a break, so the destination can read as a solid block even when the server rejected it. What confirms that a placement actually happened?

# Lösung

Decision: placement confirmation mirrors the break artifact exactly. Two signals are required: the destination must hold a non-air, fluid-free block for CONFIG.airConfirmTicks consecutive ticks, AND the main inventory must have SHRUNK since the interaction started. Why the inventory shrink: a client-predicted placement the server rejects never moves the item count, so the count is the server-authoritative half of the gate - the precise mirror of the break case, where a pickup RAISES the count (see STR-030). The fluid-free part of the state check matters for the chunk-miner use case: sealing a water source only succeeds once the water itself is gone, and a flowing-water state is neither air nor a finished placement. Important trap found while writing the test: in creative the block is never consumed, so the item count can never shrink and every creative placement would silently burn the full maxBreakTicks. player.getAbilities().instabuild therefore substitutes for the inventory signal in creative, where the sustained-state window alone is enough. Naming: the counter is now stateConfirmTicks rather than airConfirmTicks, because it counts ticks in the COMPLETED state - air when mining, a solid block when placing. The config key stays CONFIG.airConfirmTicks because it is persisted in bot.json and renaming it would silently reset user configs. Alternatives: sustained state window alone, pro: simplest; contra: exactly the failure mode the break gate was built to close, a prediction the server later reverts reads as success. Wait for a server block-update packet for the destination, pro: fully authoritative; contra: adds mixin surface for a signal the inventory count already carries. See also [[STR-053]].
