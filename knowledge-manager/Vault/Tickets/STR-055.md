# Problem

A USE task needs two things mining does not - a specific item in hand and a specific face to click. How is that carried without touching every existing task?

# Lösung

Decision: two default methods on BotTask. requiredItem() returns a Predicate<ItemStack> for the item to hold, or null meaning pick the fastest tool for the target block; preferredFace() returns the face to interact with, or null meaning re-derive the most visible face each tick. Both default to null, so MineBlockTask, ChopTreeTask and GatherAreaTask were not touched at all. What each buys: requiredItem makes LOOKING call InventoryHelper.selectItem (largest matching stack) instead of selectBestTool, which would pick a pickaxe for a placement - nonsense. selectItem shares the hotbar-swap and carried-item-packet logic with selectBestTool via an extracted private equip() helper, so the STR-040 and STR-043 guarantees hold for placement too. preferredFace pins the clicked side; mining returns null and keeps re-deriving per tick because the best visible face changes as the bot moves, while placement must not, since the face decides where the block lands. When preferredFace is non-null the LOOKING hit-result gate additionally requires bhr.getDirection() to match - clicking the wrong side of the support block would put the new block somewhere else entirely, and the block-position check alone cannot catch that. Alternatives: instanceof PlaceBlockTask in BotController, pro: no interface change; contra: the controller would depend on a concrete task type, breaking the seam that lets modules add their own tasks. A single PlacementSpec record behind one default method, pro: one interface addition instead of two; contra: an extra file to group two values that are independently meaningful, and requiredItem is not placement-specific - any future USE task (eating, bucket, torch) wants it. Abstract methods instead of defaults, pro: forces every task author to think about it; contra: churns every existing task for a value that is null in all of them. See also [[STR-040]], [[STR-043]] and [[STR-053]].
