# Problem

A block cannot be placed by aiming at the position where it should end up - the raycast passes straight through empty space and the hit-result gate never fires. What does a placement task target?

# Lösung

Decision: PlaceBlockTask.targetPos() returns the SUPPORT block, an existing block adjacent to the destination, and the task interacts with the face of that support pointing at the destination. The destination is exposed separately via placePos(). In Minecraft a block is placed on the side of the block you click, so the support plus face fully determines where the new block lands. Why this shape: the entire LOOKING pipeline - face aiming, the hit-result gate, the one-shot re-approach, the timeouts - then works unchanged, because from the controller perspective a placement is just another task pointing at a solid block. Alternatives: aim at the destination position, pro: symmetric with mining; contra: impossible, the raycast always lands on whatever sits behind the empty cell so the hit-result gate can never satisfy and every placement burns the full lookTimeout. Bypass the hit-result gate for USE tasks, pro: no support concept needed; contra: removes the correctness check that keeps the bot from interacting when the line of sight is blocked, which is exactly the guarantee that gate exists for (see STR-032). A separate placement phase in BotController, pro: placement logic kept apart from mining logic; contra: adds a parallel state machine to the most delicate class in the project for something the existing phases already express. Companion helper: PlaceBlockTask.findSupport(level, pos) returns the first neighbour whose face toward pos is sturdy (BlockState.isFaceSturdy) and null when the position is surrounded by air, fluid or non-solid blocks. Callers must skip on null rather than enqueue a task that can only time out - the same skip-and-log rule the miner already uses for unreachable ore. See also [[STR-033]] and [[STR-029]].
