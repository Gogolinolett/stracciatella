# Problem

Where should long-running automation strategies like strip mining live, given that the task queue only holds one-shot entries?

# Lösung

Decision: specialized long-running automation (strip mining, future farming or building) lives in a layer above the task queue: BotBehavior (interface with id, start, tick returning BehaviorStatus, abort, statusLine) plus a static BehaviorRunner (registry, one active behavior, ticked from the bot module before BotController.tick). Behaviors plan by enqueuing BotTasks and waiting for the controller to go idle; they never simulate input themselves. Specialized modules such as modules/miner depend on the bot module and register their behaviors at init, the same registry pattern as the pathfinding TravelMethod and Navigator. Alternatives: grow BotController phases per use-case pro: no new layer; contra: the controller phases encode how to interact with one block humanly, so mixing in what to mine next over minutes would bloat the project most delicate class and every new use-case would touch the same file. Meta-tasks in the queue extending the GatherAreaTask pattern pro: reuses the queue; contra: a queue entry is consumed once, while strategies need to observe results and re-plan (scan, mine, verify, scan) - GatherAreaTask already shows the limit since it can only pre-plan a static snapshot. Each module registers its own ClientTick hook and drives BotController ad-hoc pro: no bot-module change; contra: two modules could fight over the controller with no arbitration, there would be no shared stop semantics so /bot stop could not stop them, and no discoverability or status. Behavior layer with registry and a single active slot (chosen) pro: strategy and execution separate cleanly, behaviors own what and where next while the controller owns the human-like how, one active behavior gives natural arbitration, /bot stop stops top-down from runner to controller, and the registry pattern is already proven in this codebase; contra: one more concept and tick hook in the bot module. Rationale: the miner immediately needed observe-replan loops (verify each step, chase ore veins, fail fast on hazards) that neither the controller phases nor one-shot queue entries can express, and the next specialized modules get the same seam for free.
