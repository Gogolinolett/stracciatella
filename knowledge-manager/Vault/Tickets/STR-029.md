# Problem

The bot aims at an invisible block face and burns the full look timeout - which face of a block should it target?

# Lösung

Decision: BlockInteractor.faceTowardPlayer sorts the up-to-three player-oriented faces by how directly they point at the eye and returns the first whose neighbour block is air; only when all candidates are covered does it fall back to the dominant face. Alternatives: dominant axis only (original) pro: one comparison chain; contra: for a floor block right in front of the feet the dominant face is UP, since eye height is about 1.6 over a block roughly 1 away, but UP is still covered by the block above - the bot aims at an invisible face, the raycast hits the coverer, and the task burns the full lookTimeout before failing, observed as 11 look-timeout retries in a single miner test run while the strictly closer side face was visible the whole time. Exposed-face preference ordered by dominance (chosen) pro: picks the face a human would click, namely the most direct one that is actually visible, at a cost of three cheap isAir checks per call, and the destroy-packet direction hint improves consistently, with covered-everything falling back to dominance which callers resolve by clearing blockers first; contra: an air neighbour does not guarantee a clear ray from the eye since other blocks can still intersect the path, but the hit-result gate keeps protecting that case and the heuristic removes the common systematic failure. Full raycast per candidate face pro: exact visibility; contra: a level.clip per face per LOOKING tick for a case that three block reads already solve. Rationale: the dominant-axis bug was systematic, missing on first attempt for every floor-level block adjacent to the player, while the fix is local, cheap, and strictly more accurate as an estimate of which face can I see.
