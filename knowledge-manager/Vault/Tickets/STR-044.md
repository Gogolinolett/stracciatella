# Problem

Block breaks are instant and drop nothing at the start of a test - what must the test wait for after issuing gamemode survival?

# Lösung

Decision: BotTests.switchToSurvivalAt blocks on the player abilities flag, waiting until instabuild is false after issuing /gamemode survival, before the test enqueues its mining task. Alternatives: no wait (original) pro: simple; contra: racy under load - when the server has not processed /gamemode survival yet the player is still creative server-side, so block breaks are instant and drop nothing, the client receives an air update, airConfirmTicks fires, the bot moves on and no drop ever appeared. This was presented as a tool-select race for hours and was misdiagnosed. Large toolSettleTicks and airConfirmTicks values, tried pro: brute-forces timing margins; contra: does not fix the root cause, and every time system load changed the minimum safe value changed with it - 8, 16, 24 and 48 all flaked eventually. Wait on the ability-sync flag (chosen) pro: directly observes the server-to-client state actually needed, with no timing constants, eliminating the failure class rather than masking it; contra: adds a small wait, usually under one tick of wall time, and only in test setup. Hook ClientboundPlayerAbilitiesPacket via mixin pro: equivalent authoritative signal; contra: adds mixin surface for a check the existing Abilities field already exposes. Rationale: the ability-flag wait is the minimal, direct sync on the actual condition that matters. It was added after confirming the block-break-with-no-drop pattern also fired at the first mined position in walkMineWalkChop, ruling out the tool race as the sole cause. See also [[STR-030]].
