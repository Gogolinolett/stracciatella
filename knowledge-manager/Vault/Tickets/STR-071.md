# Problem

Auf einem echten Server bricht der Bot Bloecke nicht fertig ab: der Client sieht Luft, der Server stellt den Block wieder hin, acht Reverts in einer Interaktion, dann Block break timeout. Von Hand ist derselbe Block an derselben Stelle abbaubar. In Singleplayer und in allen In-Game-Tests unsichtbar. Woran liegt es?

# Lösung

Ursache: ein ueberzaehliges START_DESTROY_BLOCK, das der Bot waehrend des Bestaetigungs-Fensters sendet, nachdem der Client den Block schon als Luft sieht. Vanillas MultiPlayerGameMode.continueDestroyBlock entscheidet ueber sameDestroyTarget, und das vergleicht Position UND den gehaltenen Stack mit ItemStack.isSameItemSameComponents. Haltbarkeit ist eine Data-Component, also schlaegt der Vergleich fehl, sobald der Server die Beschaedigung der Spitzhacke fuer den eben gebrochenen Block zuruecksynct - und der Aufruf fliegt dann nicht ins Leere, sondern in startDestroyBlock, das ein frisches START ohne Air-Pruefung auf die Leitung legt. Serverseitig (ServerPlayerGameMode.handleBlockBreakAction, Offsets 212-217 und 346-375): START setzt destroyProgressStart bedingungslos auf gameTicks zurueck, und wenn noch ein Destroy laeuft, sendet der Server zusaetzlich den echten Blockzustand zurueck. Das folgende STOP verfehlt damit die Huerde getDestroyProgress * (elapsed + 1) >= 0.7 (Offsets 454-525), und der zurueckgesendete Zustand dreht die Client-Vorhersage zurueck. Warum es lokal nie auffiel: der integrierte Server hat den Block laengst zerstoert, wenn das Stray-START ankommt, also stirbt es in der Air-Pruefung des Servers. Wichtig fuer die Diagnose - Latenz ist NICHT die Ursache, sondern nur der Grund, warum es online sichtbar wird: sie schiebt den Haltbarkeits-Sync in das Fenster, in dem der Block serverseitig noch steht. Zweitens: ein einzeln zu fruehes STOP ist harmlos, denn der Server armiert hasDelayedDestroy und ServerPlayerGameMode.tick() bricht den Block selbst nach (Offsets 44-77) - live im Trace beobachtet, Eisenerz mit ACK -> iron_ore und zehn Ticks spaeter UPDATE -> air. Diese Selbstheilung kommt nur deshalb nie zum Ziel, weil das Stray-START die Uhr immer wieder zuruecksetzt. Fix: BlockInteractor treibt den Game Mode nicht weiter, sobald der Client den Zielblock als Luft sieht. Vanillas fuenf destroyDelay-Ticks werden ueber ein eigenes Feld airDelayTicks heruntergezaehlt und danach wird continueDestroyBlock nicht mehr aufgerufen; releaseAfterBreak uebernimmt den Rest statt neu zu armieren, sonst wuerde das Delay zweimal ausgegeben und die zweite Runde landete wieder auf dem Fall-through. airDelayTicks braucht DREI Zustaende (-1 Bruch laeuft, >0 Rest, 0 ausgegeben): ein erster Versuch benutzte dafuer cooldownPos wieder, aber tickCooldownDrain nullt cooldownPos beim Ablaufen, also war die Bedingung nach sechs Ticks wieder wahr, der Drain armierte endlos neu und die Messung aenderte sich nicht (118 START / 100 STOP vorher wie nachher). Verworfene Alternative: den Aufruf im Luft-Fall komplett weglassen - kostet die fuenf Delay-Ticks pro Block, die sonst waehrend des Wartens ausgegeben werden, und damit die Pace-Arbeit aus STR-030-Umfeld. Messmethode als Ganzes wiederverwendbar: ein temporaerer Paket-Trace (BlockWireTrace plus ein Mixin auf ClientCommonPacketListenerImpl.send sowie handleBlockUpdate und handleBlockChangedAck) protokolliert ausgehende Aktionen inklusive derjenigen fuer ANDERE Positionen - ohne die haette man das Stray-START nicht gesehen. Falsifikation ueber drei Laeufe der Suites bot,chunk: 56 START / 39 STOP mit 14 Treffern der Signatur START direkt nach Luft-Zustand, dann 118/100 mit 15 Treffern beim falschen Fix, dann 105/102 mit 0 echten Treffern. Nebenwirkung, gemessen: die Pace verbessert sich mit, Chunk miner mines without stalling von 14 von 18 bei 17.7 Ticks pro Block auf 17 von 18 bei 14.6, holds its aim sammelt 20 von 20 statt 17. Der restliche Ueberschuss (105 gegen 102) sind Neustarts mitten im Bruch auf STEHENDE Bloecke, ausgeloest vom selben Haltbarkeits-Sync - das ist vanillas eigenes Verhalten fuer einen Spieler mit gehaltener Maustaste und serverseitig harmlos, weil ein START auf einen stehenden Block legitim ist und das STOP eine ganze Bruchzeit spaeter kommt. Siehe auch [[STR-065]] fuer das Stray-ABORT auf Tick 1 und [[STR-030]] fuer die Bruch-Bestaetigung.
