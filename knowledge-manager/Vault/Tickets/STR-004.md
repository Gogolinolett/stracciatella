# Problem

Why do HashMap lookups with MeshNode keys fail when different instances share the same coordinates?

# Lösung

Decision: implement equals() and hashCode() based on the (x, y, z) coordinates. Alternatives: reference identity (original) pro: nothing to implement; contra: breaks HashMap lookups if different MeshNode instances share coordinates, a fragile assumption. Coordinate equality (chosen) pro: correct HashMap behaviour, safe to create MeshNode instances anywhere; contra: coordinates must uniquely identify a node within a mesh. Rationale: MeshNode is used as a HashMap key in MeshPathfinder (gScore, cameFrom) and compared via equals() in tests and path reconstruction. Reference identity worked by accident but was a latent bug.
