# Problem

Removing the old settle delay made the transition to mining feel too eager - should the pause come back, and under which name?

# Lösung

Decision: after the LOOKING gate fires but before the first startAttack call, hold for a short uniform preAttackHesitation window (default 1-3 ticks, roughly 50-150 ms). During the window the camera keeps aiming and micro-saccades are enabled. This is a distinct concept from the removed settleDelay - it is humanness, not a timing buffer for packet sync. Alternatives: no pause at all, the state after the cleanup commit pro: fastest transition, reading as adjust then mine in one motion; contra: loses the visible human commit moment between locking on and clicking, and combined with the spring-damper camera the transition feels too eager, particularly visible block-to-block in a vein where the bot is otherwise standing still. Re-add the old settleDelay of 2-5 ticks pro: restores some humanness; contra: the old delay was framed as a timing buffer for the server carried-item packet, and that buffer is no longer needed since tool selection now happens during the LOOKING camera turn, so keeping the same name and timing would conflate two different reasons for the same pause. Pre-attack hesitation of 1-3 ticks under a distinct name (chosen) pro: a narrower window than the old settle, clearly labelled as humanness, with saccades starting here so the gaze trembles during the commit moment; contra: adds 50-150 ms per block break, within the authorised small reliability degradation budget. Rationale: the cleanup commit was right to remove the old delay since it solved a problem that no longer existed, but removing it entirely also removed the bit of humanness that pause was inadvertently providing. The new field reintroduces that humanness with half the duration and a clear semantic separation - tool-selection sync is handled by parallel packet sending during LOOKING, while the hesitation here is purely the human I see it, I click beat.
