# Problem

Why send ServerboundSetCarriedItemPacket even when the client selected slot is already correct?

# Lösung

Decision: InventoryHelper.selectBestTool sends ServerboundSetCarriedItemPacket every time it selects a slot, even if the client-side selectedSlot is already at that index. Alternatives: setSelectedSlot only (original) pro: minimal; contra: a client-only change, so the server held-item state may diverge and break or drop calculations then use the wrong tool. Send the packet only when bestSlot differs from the current slot pro: slight bandwidth saving; contra: requires trusting that client and server are in sync, which they are not always, especially across tests. Send the packet always (chosen) pro: cheap, idempotent and guarantees server agreement; contra: one extra packet per interaction start, which is negligible. Rationale: the packet is tiny and idempotent, while a stale server-side slot is a silent-failure mode where drops are computed with the wrong tool - worth the trivial cost. See also [[STR-040]].
