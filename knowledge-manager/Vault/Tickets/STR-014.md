# Problem

EnderPearl tests flake under accelerated ticks because the throw is rejected - where should the item cooldown be waited out?

# Lösung

Decision: EnderPearlTests waits on the client-side ItemCooldowns, synced from the server via ClientboundCooldownPacket, and then adds a 30-tick safety margin before calling EnderPearlTravelMethod.start(). The travel method itself does not check or clear the cooldown. Alternatives: a fixed waitTicks(N) larger than 20 only pro: simple; contra: non-deterministic under accelerated ticks, different -PtickSpeed values need different N. Poll the cooldown in test setup plus a 30-tick safety margin (chosen) pro: deterministic on the client side, authoritative because it is server-synced via packet, and it scales with any tick rate while the margin absorbs client/server tick-rate drift; contra: tests must know to poll, which couples the test to the cooldown mechanic. Check the cooldown inside EnderPearlTravelMethod.tickThrowing pro: encapsulated; contra: a compensating wrapper around a test-harness ordering issue, and the method should not silently delay callers who asked for a throw. Rationale: the travel method correctly fails when a throw is ignored, so the test setup phase is the right place to establish preconditions. The 30-tick safety margin handles client/server tick drift: the client ItemCooldowns can clear ahead of the server under -PtickSpeed above 1 when the frame rate outpaces the tick rate, and a client-side use press during that gap is silently rejected by the server.
