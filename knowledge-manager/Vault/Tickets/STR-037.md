# Problem

The bot visibly zigzags across an area because tasks run in scan order - how is the next task chosen?

# Lösung

Decision: whenever the bot takes the next task from the queue - in startNextTask, the within-reach continuation in tickInteracting, and the walk-flow exit in tickCollecting - it takes the task whose target is nearest to the player current position via TaskQueue.pollNearest and peekNearest, with ties keeping insertion order, instead of the queue head. Explicit single commands still run in submission order, since a single-element queue is unaffected. Alternatives: FIFO in scan order (original) pro: deterministic and trivial; contra: BlockScanner sorts by distance to the scan center, so equidistant targets on opposite sides interleave and the bot visibly zigzags across the area, which no human does, and the order also ignores where the bot ends up after each task. Re-sort the whole queue after every task pro: same routing result; contra: mutates global order on every poll for no benefit over picking one element, and is harder to reason about with concurrent enqueues. Greedy nearest from the current position (chosen) pro: matches how a player works an area by finishing here and doing the closest thing next, at O(n) per poll over a small queue, with ties preserving FIFO so single-task flows and equal-distance tests stay deterministic; contra: greedy is not the globally optimal route, which is fine because humans are not optimal either. Nearest with a random second choice to model human suboptimality pro: models human imperfection; contra: deliberately re-introduces the zigzag the change removes, and randomness in route choice, as opposed to timing or aim, reads as erratic rather than human. Rationale: the visible failure mode was routing, and nearest-from-here is both the simplest fix and the most human-plausible heuristic.
