# Problem

The bot keeps punching an already-broken block for 400 ticks when standing right next to it - why does the drop-entity check miss the drop?

# Lösung

Decision: poll the drop AABB on every INTERACTING tick and latch the result (dropSeenThisBreak) so a drop that exists for even one tick counts, and additionally accept growth of the main-inventory item count since break start as an alternative artifact. Evidence and problem: the original implementation queried the drop AABB only once the sustained-air window was already satisfied. That has a hole when the bot stands right next to the block, as in gallery mining or close-range re-approach: vanilla pickup inhales the drop within a tick of spawning, so no post-air query ever sees it, and the bot then kept attacking the already-broken block for the full maxBreakTicks - 400 ticks, which is 20 seconds of punching air in real time, with timestamped task-fail logs showing five such 400-tick stalls in one run. Why the inventory-growth signal is valid: the pickup itself is server-driven via slot sync, so it proves the break as authoritatively as the entity did. Risk assessment: a false positive would need the client air prediction plus an unrelated simultaneous pickup, and if the server then reverts, the planner verify step sees the solid block and re-plans, so the failure stays contained. See also [[STR-030]].
