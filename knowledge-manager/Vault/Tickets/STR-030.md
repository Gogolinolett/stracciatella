# Problem

The client shows air after a block break but the server reverted it and no drop ever spawned - how is a break confirmed?

# Lösung

Decision: INTERACTING requires two authoritative signals before transitioning out: a sustained-air window of CONFIG.airConfirmTicks consecutive ticks (default 8), and a drop entity existing within a 5x5x5 AABB around the target. Alternatives: single-tick isCurrentTargetComplete check (original) pro: minimal; contra: under accelerated ticks the client break prediction races ahead of the server, so the client shows air and the bot transitions while the server rejects and restores the block, and no drop spawns. Sustained-air window only pro: zero new infrastructure; contra: client-side sequenced-transaction prediction can hold the predicted-air state for a long time before the server revert ack arrives - under tickSpeed=20 an observed lastMinedPos state=iron_ore at COLLECTING exit proved the server never broke it, yet airConfirmTicks had fired, so no fixed window size is safe. Air plus drop entity (chosen) pro: the drop entity is authoritative because the server only spawns it after actually completing the break, so if the client air is a mere prediction the server later reverts, no drop entity ever appears and the bot keeps mining until maxBreakTicks - and it works independently of tick-rate jitter; contra: adds a per-tick AABB query once airConfirmTicks is satisfied, which is cheap for a 5x5x5 region, and for blocks that break with no drop such as wrong-tool breaks, INTERACTING runs to maxBreakTicks and fails the task, which is correct behaviour since no drop is useless anyway. Listen for ClientboundBlockUpdatePacket via mixin pro: authoritative; contra: requires a packet-pipeline mixin, while the drop-entity check uses an existing entity query of equivalent signal quality. Higher server tick rate to outpace the client pro: eliminates the race at the source; contra: can starve other server work and not all dev machines support it. Rationale: this is the first approach that is load-independent. Earlier attempts at tuning windows (3, 8, 16, 32, 48 ticks for airConfirmTicks or toolSettleTicks) passed in some runs and flaked in others depending on system load, whereas the drop-entity check relies on an actual server-side artifact rather than a timing assumption - the block broke if and only if the drop exists. See also [[STR-031]] and [[STR-044]].

## Update 2026-09-07 13:37:44

NACHTRAG 2026-09-07 - der Server-Ack ersetzt das Fenster als schneller Weg. Das damals verworfene Argument gegen ein Packet-Mixin galt fuer ClientboundBlockUpdatePacket; das richtige Paket ist ClientboundBlockChangedAckPacket. Abbauen ist eine sequenzierte Client-Prediction: MultiPlayerGameMode.startPrediction erhoeht BlockStatePredictionHandler.currentSequence und schickt die Nummer mit, der Server antwortet mit dem Ack zu dieser Sequenz, und handleBlockChangedAck ruft endPredictionsUpTo - das schliesst jede Vorhersage bis dorthin ab und rollt alles zurueck, wo der Server widerspricht. NACH dem Ack IST die Client-Sicht auf diesen Block die Server-Sicht; genau diese Tatsache hat das Luft-Fenster plus Artefakt nur angenaehert. Umsetzung: ServerBlockSync merkt sich die hoechste bestaetigte Sequenz, gefuettert von einer Injection in ClientPacketListener.handleBlockChangedAck. TAIL, nicht HEAD - aus demselben Grund wie die beiden Alarm-Injections dort, PacketUtils.ensureRunningOnSameThread laeuft einmal auf dem Netty-Thread, und hier zusaetzlich, weil erst am TAIL der Revert stattgefunden hat. INTERACTING sampelt currentSequence im ersten Tick, in dem das Ziel fertig aussieht, und verlaesst die Phase, sobald diese Sequenz bestaetigt ist. Fenster plus Artefakt bleiben als Fallback fuer eine Verbindung, die nie ackt. Falle: ClientLevel.getBlockStatePredictionHandler ist package-private, daher der Mixin-Invoker ClientLevelAccessor. Gegen die urspruengliche Race abgesichert: lehnt der Server ab, revertet endPredictionsUpTo den Block noch vor dem naechsten Client-Tick, isCurrentTargetComplete wird falsch und completionSequence faellt auf -1 zurueck. MESSUNG statt Schaetzung, gleiche Suite, dieselben 14 Bloecke, INTERACTING-Dauer je Block: vorher 15 15 15 15 15 15 15 15 15 15 15 17 18 20, Mittel 15,7 - nachher 10 10 11 12 12 13 14 14 14 14 14 16 16 20, Mittel 13,6. Der harte Boden bei 15 Ticks, also das airConfirmTicks-Fenster, ist weg. Der Gewinn betraegt aber nur 2,1 Ticks statt der 8 Ticks Fenstergroesse, weil die Ack-Runde selbst Zeit kostet: wer aus der Fenstergroesse auf die Ersparnis schliesst, ueberschaetzt sie um das Vierfache. Kompletter Zyklus LOOKING plus INTERACTING 21,3 auf 19,7 Ticks.
