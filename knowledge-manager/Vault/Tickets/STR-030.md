# Problem

The client shows air after a block break but the server reverted it and no drop ever spawned - how is a break confirmed?

# Lösung

Decision: INTERACTING requires two authoritative signals before transitioning out: a sustained-air window of CONFIG.airConfirmTicks consecutive ticks (default 8), and a drop entity existing within a 5x5x5 AABB around the target. Alternatives: single-tick isCurrentTargetComplete check (original) pro: minimal; contra: under accelerated ticks the client break prediction races ahead of the server, so the client shows air and the bot transitions while the server rejects and restores the block, and no drop spawns. Sustained-air window only pro: zero new infrastructure; contra: client-side sequenced-transaction prediction can hold the predicted-air state for a long time before the server revert ack arrives - under tickSpeed=20 an observed lastMinedPos state=iron_ore at COLLECTING exit proved the server never broke it, yet airConfirmTicks had fired, so no fixed window size is safe. Air plus drop entity (chosen) pro: the drop entity is authoritative because the server only spawns it after actually completing the break, so if the client air is a mere prediction the server later reverts, no drop entity ever appears and the bot keeps mining until maxBreakTicks - and it works independently of tick-rate jitter; contra: adds a per-tick AABB query once airConfirmTicks is satisfied, which is cheap for a 5x5x5 region, and for blocks that break with no drop such as wrong-tool breaks, INTERACTING runs to maxBreakTicks and fails the task, which is correct behaviour since no drop is useless anyway. Listen for ClientboundBlockUpdatePacket via mixin pro: authoritative; contra: requires a packet-pipeline mixin, while the drop-entity check uses an existing entity query of equivalent signal quality. Higher server tick rate to outpace the client pro: eliminates the race at the source; contra: can starve other server work and not all dev machines support it. Rationale: this is the first approach that is load-independent. Earlier attempts at tuning windows (3, 8, 16, 32, 48 ticks for airConfirmTicks or toolSettleTicks) passed in some runs and flaked in others depending on system load, whereas the drop-entity check relies on an actual server-side artifact rather than a timing assumption - the block broke if and only if the drop exists.
