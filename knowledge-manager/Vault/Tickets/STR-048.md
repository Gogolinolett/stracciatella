# Problem

Should the strip miner handle hazards like lava and caves, or abort the run?

# Lösung

Decision: liquids ahead or overhead, bedrock in the dig path, a missing floor and open caves abort the run with a reason (FAILED plus a status line). Only two soft cases exist: a single-slice air pocket is tunneled through, and an unreachable or blocked ore is skipped via a remembered skip-set. Alternatives: handle hazards by placing blocks against lava, bridging holes and lighting caves pro: autonomous long sessions; contra: requires block placement, inventory management and a USE interaction path, none of which the task layer has yet - each is its own project, and bolting naive versions on risks drowning the bot in lava on the first edge case. Ignore hazards pro: simplest; contra: the bot walks into lava at diamond level, the single most common way to lose a session. Fail fast with a reason (chosen) pro: the dangerous cases become clean, explainable stops so the user repositions and restarts, matching the project authoritative state over hope testing philosophy; contra: runs end early in hazardous terrain. Skip and reroute around hazards pro: keeps mining; contra: re-planning the tunnel line around obstacles is real pathfinding through unmined volume, out of scope for v1 and partially covered anyway by restarting in a new direction. Rationale: fail-fast was chosen because the cost of a wrong hazard guess, lava, is total while the cost of a clean stop is one chat message. The ore skip is the exception because a single unreachable ore is local, harmless, and should not kill an hour-long run.
